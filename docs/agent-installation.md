# 墨叽 DSH 原生插件安装与更新

本文适用于首次安装、同名插件更新，以及从旧「催更姬」迁移到墨叽。**优先安装已核实的 DSH 插件 `.tgz` 包，不要求普通用户先安装 Git 或编译源码。**目标版本以所选包的 `package.json` 为准，不固定某个版本号。

基本流程：**确认环境与包 → 备份 → 原生插件管理安装 → 完整重启 → 核对版本和作品。**本文不要求配置 MCP 或部署云端；DSH 原生插件就是本次安装入口。

## 1. 确认宿主、旧插件和数据

- 记录实际 DSH 版本、当前 profile、已安装的插件名／版本及启用状态。兼容范围以目标包的 `engines.dsh` 和宿主检查结果为准，不强行跳过不兼容检查。
- 已有作品时，记录实际数据根、作品 ID 与数量，以及卷章、设定、规划、历史和绑定等可取得的清单。不要套用他人的用户名、目录或作品数量。
- 数据根优先级：宿主配置 `dataRoot` → `MOJI_DATA_ROOT` → 兼容变量 `CUIGENGJI_DATA_ROOT` → 系统默认目录。Windows 默认基目录通常为 `%LOCALAPPDATA%`：已有 `cuigengji` 子目录就沿用，否则使用 `moji`。**改名不会自动搬家；显式配置优先于默认目录检测。**
- 保留原插件配置、DSH Home、聊天、附件和桌面偏好。旧版本没有维护工具时，可用旧插件的 `settings.get` 和只读作品清单核对；不要为安装而新建空库。

有管理权限的 DSH Agent 可先调用 `plugin_manager`，并按 `nextOffset` 翻页，取得准确包名：

```json
{"action":"list_bundles","offset":0,"limit":100}
```

没有此工具时使用 DSH 原生插件页面；也可切换到宿主提供管理工具的模式。工具权限、审批与构建脚本批准均遵循宿主机制，不因安装授权而自动放行额外操作。

## 2. 取得并核对 DSH 插件包

从[项目 Releases](https://github.com/CF-612/MoJi/releases)中**实际可访问的发布条目**选择 DSH 插件资产 `dsh-moji-<版本>.tgz`，或使用维护者已提供且能核实来源的本地包。

- 阅读发布说明，区分稳定版与预发布／候选版；使用预发布包前明确其试用性质。需要当前候选版新功能时选择对应候选包，不仅按 `latestStable` 取旧稳定包。草稿或无权访问的资产不算可下载发布，不猜测下载 URL。
- 核对包内 `package.json` 的名称、版本和兼容声明，记录包的绝对路径及 SHA-256；如发布方提供校验值，应逐项比对。只有本地算出的哈希不能证明来源可信。
- **Windows 独立版 ZIP、源码 ZIP、旧上游插件包都不是 DSH 原生插件 `.tgz`。**不要改扩展名或重命名旧包充当升级，也不要假设 npm 注册表已经发布了 `dsh-moji`。
- 成品包已有运行产物，无需用户运行 `npm pack`；安装时宿主仍可能解析依赖，不能据此承诺完全离线。系统 Node/pnpm 版本不是插件实际运行时版本，按宿主及目标包要求判断。

没有合适的已核实包时，见下方「开发者备用：源码构建」，不要退回不相关的旧包。

## 3. 先备份，再由原生插件管理安装

先保存编辑内容、导出作品备份，并保存当前 profile 配置（如 `package.json`、锁文件、`cordis.patch.yml`）和旧包信息。需要完整复制数据目录时，先正常退出宿主及托盘，避免边写边复制；备份完成后重新打开宿主使用原生安装入口。备份应存放在原数据根之外，并确认能够读取。

区分三种情况：

| 情况 | 操作 |
| --- | --- |
| 首次安装 | 直接安装新包；不要动其他插件或现有资料目录。 |
| 已有 `dsh-moji`，更新同名包 | 原位更新并保留配置／启用状态；不必先卸载旧版。 |
| 从 `dsh-cuigengji` 改名迁移 | 先通过原生管理停用并移除旧插件本身，**保留作品目录和备份**，再安装墨叽并核对原数据根。不要同时启用两个写入同一作品库的实例。 |

通过 DSH 原生插件页面选择 `.tgz`；Agent 可调用同一管理服务的 `plugin_manager`。以下路径只是占位符，必须替换成已核实包的真实绝对路径；`enabled` 应按用户原启用状态和意图设置：

```json
{"action":"install_bundle","target":"<本地插件包的绝对路径>","enabled":true}
```

旧包迁移使用 `list_bundles` 查到的准确包名，通过 `set_bundle`（`enabled:false`）停用、`remove_bundle` 移除；不手工删除作品文件。读取安装返回的 `application`、`error`、`packageResult` 等诊断，处理宿主要求的批准。`restart-required` 仅表示需重启，不能说明当前进程已经加载新代码。

**desktop profile 由桌面宿主管理。**普通 CLI 拒绝管理它时，改用原生管理入口；不要通过手改 bundles、在 profile 运行 `pnpm add/install` 或创建同名 profile 绕过限制。手工修复仅限备份充分、明确授权的专门排障，不是普通安装步骤。`install-dsh-native.mjs` 是开发者更新脚本，不是首次安装或旧包迁移的通用入口。

## 4. 完整重启并核对实际加载结果

保存内容，从 DSH 菜单正常退出，确认托盘进程也退出，再从原入口启动。插件会在加载阶段执行需要的备份、恢复、迁移和校验；通常不需要手工运行迁移命令。即使新旧存储版本相同，也不能省略完整性验收。

对于本机作品库，重启后调用不要求绑定小说的 `moji_maintenance`：

```json
{"action":"status","args":{}}
```

确认返回的 `status` 为 `ready`。随后核对目标包版本、原数据根和升级前作品 ID；下列值均须替换为实际记录，首次安装没有旧作品时才使用空 ID 数组：

```json
{"action":"verify","args":{"expectedVersion":"<目标包版本>","expectedDataRoot":"<实际数据根绝对路径>","expectedNovelIds":["<原作品ID>"]}}
```

确认 `verified=true`，并对照返回的 `summary` 及升级前清单检查章节、正文历史、回收站、设定、规划和绑定等内容。仅看磁盘包版本、侧栏出现、依赖安装成功或 headless 实例等待 UI 服务，都不足以证明真实宿主验收完成。

再打开墨叽工作台，确认原作品可打开、目录与正文可读。首次安装应可使用空库，不应附带别人的小说。保存／持久化检查请使用临时测试作品或用户同意的副本，不改动原稿；确认保存后关闭重开，必要时重启宿主后再核对。不能完成的检查明确标为待验收，不把安装报告当成实测。

以上不要求额外调用模型连通性测试。外部 Agent 也可通过同一 DSH 连接、正常宿主认证的兼容 RPC `cuigengji/dispatch` 查询 `maintenance.status` / `maintenance.verify`；内部旧名称不是另装旧插件的理由，不打印连接凭据。

如用户原先连接个人云端，应保留原连接，不擅自切回本机或创建新库；本机数据根校验不能替代云端作品核对。本机库和云端库不会自动同步。云端部署不是本次插件安装步骤，另见 [README](../README.md#部署自己的个人云端实例)。

最终报告只需说明：**实际加载版本、校验结果、原作品是否保留、尚未完成的检查。**

## 5. 常见问题与安全回滚

- **安装仍要求 Git／找不到 `git ls-remote`**：先检查是否误选仓库地址或源码安装；已有核实 `.tgz` 时应选择本地包。
- **不兼容、缺少依赖或等待构建批准**：保留原生管理返回的具体诊断，按目标包发布说明处理；不要擅自豁免版本或批准依赖脚本。
- **重启后仍是旧版本**：核对 profile、安装结果、完整退出情况及维护工具返回的实际加载版本。
- **`request/header` 提示不可 JSON 序列化**：不能直接归因于宿主或断言“重启就修好了”；插件工具元数据缺失等问题也会触发。保留目标包版本、宿主版本、复现步骤及脱敏日志，核对修复说明。重启后暂时恢复不等于排除插件原因，不指导用户临时修改已安装包来掩盖问题。
- **迁移 `failed` 或作品缺失**：保留 `failedStage`、错误代码、`backupPath` 和实际数据根；先比对原作品 ID 与目录，不创建空替代库。挂起升级可在完整重启后恢复，反复失败时交维护者诊断。
- **命令行预检被工作目录环境配置拦截**：预检不等于宿主安装；遵循宿主环境变量规则，不把密钥复制到教程或日志，也不为绕过检查改动用户配置。
- **确需回滚**：先完整停止宿主并保留升级后新写入；使用对应旧包和升级前快照，在**新的恢复目录**验证可读取及数据完整后再切换配置。不要直接覆盖原数据根。只换旧包不等于数据回滚，恢复范围须由用户确认。

完整快照和恢复边界见[更新与数据迁移](upgrade.md)。共享日志前移除凭据、私人路径和作品内容。

## 开发者备用：源码构建

仅在没有合适成品包或确需开发验证时使用。选择维护者说明的源码分支／标签／提交，不混用仓库默认分支的历史说明；按所选源码 `package.json` 和锁文件准备兼容的 Node.js、npm 与 Git。在源码根目录执行：

```sh
npm ci
npm ci --prefix integrations/chatgpt-workbench
npm pack
```

`npm pack` 会运行类型检查与构建。核对真实成功、生成的 `dsh-moji-<版本>.tgz` 及哈希，再回到本文原生安装步骤。构建成功不等于安装或宿主验收成功。未经授权不替用户安装依赖、修改宿主或创建云资源。

个人云端部署是独立任务，见[云端部署执行边界与本地验收](cloud-agent-deployment.md)。
